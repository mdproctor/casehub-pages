Comparison: What Java Would Look Like

The same barrier-with-staggered-delays pattern, reviewed as a Java PR. The reviewer gets a text diff. They must mentally trace the ExecutorService, CountDownLatch, and thread interactions.

// Java equivalent of the 3-branch barrier example
var executor = Executors.newFixedThreadPool(3);
var barrier = new CyclicBarrier(3);
 
executor.submit(() -> {
  click("A");               // fast — no delay
  barrier.await();
  click("D");
});
executor.submit(() -> {
  click("B");
  Thread.sleep(1000);     // medium — 1s delay
  barrier.await();
  click("E");
});
executor.submit(() -> {
  click("C");
  Thread.sleep(2000);     // slow — 2s delay
  barrier.await();
  click("F");
});
 
// 15 lines of code to mentally trace.
// The barrier semantics are implicit in the API name.
// Adding a 4th branch is a multi-line diff with a
// CyclicBarrier(3→4) change buried in line 2.
The Java version: 15 lines of text. The reviewer mentally constructs the swim lanes in their head. Adding a 4th branch = +6 lines of new code, +1 line changed (barrier count), all interleaved in a text diff.

The step viewer: The swim lane diagram IS the review surface. Adding a 4th branch = a new green lane appears, barrier count shows 3→4 inline. Verified in seconds, not minutes.

trade signals flow through progressive abstraction levels

Progressive abstraction: Raw trade events (thousands/second) → per-instrument grouping → windowed anomaly classification (threshold rules as a mini-table) → phase detection (state machine: NORMAL → ELEVATED → CRITICAL). Each level emits a new CloudEvent type. The reviewer sees the full signal-processing pipeline at a glance — impossible in Java where this would be spread across event handlers, scheduled jobs, and state machine classes.
